# Native advanced search verification

`createSearchFolder` uses the public ISearchFolderItemFactory pipeline: parsed/resolved ICondition, IShellItemArray scope, GenericSearchResults type and Details presentation. The [documented factory](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-isearchfolderitemfactory) exposes no contents/system/archive option setter. [SetScope](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-isearchfolderitemfactory-setscope) includes the supplied location and subcontainers; [System.Search.Contents](https://learn.microsoft.com/en-us/windows/win32/properties/props-system-search-contents) is a query restriction, not a retrievable result property. The public [saved-search format](https://learn.microsoft.com/en-us/windows/win32/search/-search-savedsearchfileformat) explicitly reserves provider/condition attributes for internal use, so the application does not invent undocumented XML option flags.

Local read-only Windows 10 Home 22H2 build 19045 inspection found installed CommandStore handlers:

| Exact command | Installed ExplorerCommandHandler |
|---|---|
| Windows.SearchOptionContents | {576C5669-E07F-4A1B-9A7A-8F85D944283B} |
| Windows.SearchOptionSystem | {263A4743-BC0D-40B6-8F7F-1B2135C204D2} |
| Windows.SearchOptionCompressed | {E2F33E30-B587-4F08-BF1A-F28D0F41000A} |

All three have CommandStateSync. On an actual hidden IExplorerBrowser search view, all three native menu leaves were present and enabled. The initial popup enumeration exposed no MFS_CHECKED bits. Reading the actual [IExplorerCommand::GetState(FALSE)](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iexplorercommand-getstate) instead shows Contents unchecked, System checked and Compressed unchecked on the local Windows 10 system. The generic CommandStore popup therefore does not represent these Ribbon checkmarks reliably.

A generic term present only in an owned TXT's content returned zero results, while an explicit `System.Search.Contents:` restriction returned that exact file. Thus content extraction works independently of unqualified-term expansion; no filter/index change is needed for this fixture. An owned ZIP member filename query returned zero results; a separate native compressed-folder enumeration proved that the ZIP is valid and contains exactly that member. A filename inside an owned SYSTEM+HIDDEN folder returned one result with the real System option checked. This baseline does not establish unchecked-System behavior or coverage of protected Windows system directories.

Scoping the same filename condition directly to the native ZIP folder returned its member, while the parent physical-folder scope returned zero with the Archive checkbox off. The compressed-folder provider and public factory can therefore search that member without extraction; the option controls discovery/traversal from its parent scope rather than enabling basic ZIP querying.

The read-only audit never invoked a command, showed a menu/window, extracted an archive, modified the search index or wrote a setting. Byte/type/value/key snapshots of Explorer Advanced, Search and SearchPlatform were unchanged. Baselines alone do not establish whether an option changes current/subsequent query behavior; that needs the separate mutation test.

`native_search_options_tests` is the separate mutation test. Its ordinary build checks both `GITHUB_ACTIONS=true` and `WINDOWSEXPLORER_SEARCH_OPTIONS_TEST=1` before COM, HWND creation or files. Each invocation and any settings restoration rechecks both gates. The fixture owns its temporary scope, content file, synthetic system folder and valid stored ZIP. It invokes only the enumerated enabled native option ordinal with NO_UI, NOASYNC and SW_HIDE. WinEvent/polling observes both process-owned visible windows and newly visible top-level Shell/surrogate windows. There is no active window, clipboard access or Recycle Bin operation.

The disposable-VM test uses actual production namespaceCommandState/GetState(FALSE) as checkbox authority and retains popup MFS_CHECKED only as a diagnostic. It compares unchecked and checked current-provider results, then creates a fresh search through the exact app pipeline and requires both native checked state and result identities/count. It restores each original native state on success/failure and restores exact original setting values/types/absence after closing the view. It requires real content/archive result changes and fresh-query parity; a mismatch fails rather than being described as functional parity. The synthetic System case checks native state transitions and provider/fresh-query consistency without claiming protected-system-directory coverage.

`WINDOWSEXPLORER_SEARCH_OPTIONS_READ_ONLY_AUDIT` is used only by the isolated local audit build: every native invocation is rejected in that build, regardless of environment variables. Both builds compile cleanly with MSVC /W4. The real toggle fixture has not been executed locally. Ribbon checkmarks must use actual IExplorerCommand state rather than locally flipped Boolean fields or an unchecked generic popup entry.

The [initial hosted probe](https://github.com/ProtonDev-sys/windows-explorer/actions/runs/37191197093) stopped during ZIP fixture name validation before any option invocation, reporting zero setting differences. Fixture identity now compares PKEY_FileName, with an in-folder parsing-name fallback, instead of a normal display label that can hide known extensions. Diagnostics include both names, STRRET types and native item-type metadata. A subsequent fixture correction derives long, raw, Shell and 8.3 aliases exclusively from the owned existing root. Native results retain a strict ownership prefix guard and normalize to the root's long name. An owned 8.3 query scope was verified locally with a read-only query.

The [hosted diagnostic probe](https://github.com/ProtonDev-sys/windows-explorer/actions/runs/37193154921) established native Contents behavior: InvokeCommand succeeded, GetState(FALSE) returned ECS_CHECKED (0x8), and the exact owned content-only file appeared in the existing provider and a fresh app-factory query, including a new hidden browser host. The changed setting was Explorer\\Search\\PrimaryProperties\\UnindexedLocations\\SearchOnly DWORD 0 and was restored. The generic popup still omitted MFS_CHECKED, causing the older test's checkbox assertion to fail even though native state and content results were correct.

The [complete hosted verification](https://github.com/ProtonDev-sys/windows-explorer/actions/runs/37194199690) at commit `928dfcd` passed all four isolated tests. Actual native Undo/Redo with production fast-state equivalence passed in 2.79 seconds; the Contents/System/Compressed fixture passed in 2.25 seconds. All three checkbox OFF/ON transitions were read through public GetState(FALSE). The content-only file and ZIP member had the required exact OFF/ON result changes, and newly created searches through the application's unchanged public factory had matching state and owned result identities/count. The synthetic SYSTEM+HIDDEN folder passed the defined native-state/provider/fresh-query consistency checks; this still makes no claim about protected Windows-directory coverage. Every original native option state and exact registry value/type/absence was restored, and the visibility observer found no visible windows. These verified transitions show that the public factory pipeline honors native options without separate application Boolean flags or undocumented query-provider attributes.
