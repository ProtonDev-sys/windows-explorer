# Search suggestions version and API audit

Research date: 2026-10-04. This records requirements and uncertainty, not a passing suggested-file UI test. The inspected machine reports Windows 10 Home 22H2, build 19045.6466. No Explorer process was launched, no feature flag or setting was changed, and no personal search/history/index results were inspected.

Microsoft's [May 2019 Explorer announcement](https://blogs.windows.com/windows-insider/2019/05/08/announcing-windows-10-insider-preview-build-18894/) describes a Windows Search powered dropdown of matching files, including online OneDrive content. Clicking a result opens it; its context menu can open its location. Enter opens traditional search results, including non-indexed locations. Focusing the empty box displays search history. Its [original illustrated screenshot](https://blogs.windows.com/wp-content/uploads/prod/sites/2/2019/05/c091099f131f65e0eebfedbdfd3ab842.png) has a declared display size of 640 × 337, but that is not an established native-resolution/DPI baseline for the installed OS. It is linked for provenance and not redistributed as application artwork.

The Windows 10 section of Microsoft's [current screen-reader instructions](https://support.microsoft.com/en-us/accessibility/windows/use-a-screen-reader-to-explore-and-navigate-file-explorer-in-windows) also describes suggested top results below the box, Down/Enter activation, Escape dismissal and Enter to display all results. These pages establish the documented modern behavior. They do not establish that every later patched 19045 installation still enables that implementation.

Microsoft's [2023–2024 DMA rollout announcement](https://blogs.windows.com/windows-insider/2023/11/16/previewing-changes-in-windows-to-comply-with-the-digital-markets-act-in-the-european-economic-area/) identifies changes beginning with 19045.3758 and later EEA rollout at 19045.4123. It does **not** explicitly document an Explorer dropdown rollback. Public reports of classic-search restoration are a reason to check the actual build/source state; they are not substituted for a public Microsoft API contract. The modern 2019 result dropdown must therefore remain a version-dependent audit item until a matched installed-state or screenshot baseline establishes it. A classic magnifier screenshot alone proves neither live-query timing nor result behavior.

At the initial audit, source supplied recent query strings to native `IAutoComplete2`; it did not supply file identities or a suggested-file activation/context-menu model. The public [autocomplete initialization contract](https://learn.microsoft.com/en-us/windows/win32/api/shldisp/nf-shldisp-iautocomplete-init) consumes `IEnumString` completion candidates. It is not a reusable Explorer result-picker interface. The missing classic `EN_CHANGE` results-pane route is addressed by the bounded scheduling and native query verification described in [classic live search](live-search-verification.md). That route does not turn history-string completion into the 2019 matching-file popup.

For a future matching-file implementation, the documented [ISearchQueryHelper](https://learn.microsoft.com/en-us/windows/win32/api/searchapi/nn-searchapi-isearchqueryhelper) supplies AQS/NQS-to-SQL conversion, a SystemIndex connection string, selected properties, sort order, restrictions and a result cap. Microsoft's [query helper guide](https://learn.microsoft.com/en-us/windows/win32/search/-search-3x-wds-qryidx-searchqueryhelper) shows querying through OLE DB, ranking, query-term expansion and locale handling. This provides a public option for bounded indexed results on a worker; it does not promise the exact private Explorer popup, federated OneDrive behavior or arbitrary non-indexed results.

Any implementation needs an identity-bearing result model separate from history strings, cancellation/generation checks, retained original Shell items, native icon retrieval without hydration, keyboard and accessibility behavior, and normal-only associated-file/location activation. The indexed dropdown and Enter/full search must retain distinct semantics. A classic live-search implementation instead needs measured debounce, stale-result cancellation, unchanged search origin and scope, and a native content-pane result transition. Existing parser compatibility guards remain mandatory; no known unsafe native filename-prefix condition is reintroduced by either route. Tests must use owned results and private desktops, with no user history, index configuration, feature-setting mutation or associated-app launch.
