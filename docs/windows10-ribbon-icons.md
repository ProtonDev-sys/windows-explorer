# Windows 10 Ribbon icon verification

The installed command handler is the first source of icon metadata. The public [IExplorerCommand::GetIcon](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iexplorercommand-geticon) returns an ordinary DLL/resource string; [SHDefExtractIconW](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shdefextracticonw) resolves negative resource IDs at the requested pixel size. This retains native artwork and DPI variants without redistributing Windows assets.

Read-only inspection on Windows 10 Home 22H2 build 19045 found three important differences between registry Icon values and actual native handlers:

| Command | Registry Icon | Native GetIcon result |
|---|---|---|
| Windows.ShareSpecificUsers | absent | imageres.dll,-178 |
| Windows.SharePrivate | imageres.dll,-5369 | imageres.dll,-59 |
| Windows.RibbonPermissionsDialog | absent | imageres.dll,-5364 |

All three GetIcon and GetTitle calls returned S_OK without command invocation, a view site or any window creation. SpecificUsers and SharePrivate implement IInitializeCommand, although their icon/title calls also succeeded without initialization in this read-only probe. Production metadata initializes registered providers where supported and can supply the real view/selection.

The stock Share screenshot contains a folder/people gallery icon, a three-dimensional gold lock, and a checklist window. The native results above match those shapes. Resource imageres,-1304 is a different, flat gold lock and must not be substituted. Registry imageres,-5369 is a people/deny icon and visibly differs from the stock Ribbon. At 16 pixels, SpecificPeople imageres,-178 is identical to shell32,-267; the native handler's own resource string should be preferred.

The View Ribbon is a separate case: the stock Preview icon is a blue right pane without text lines, shell32,-16757; the stock Details icon has horizontal lines in its right pane, shell32,-16814. The Windows.previewpane and Windows.readingpane registry Icon values select the opposite artwork. These two Ribbon image overrides preserve the commands' actual action mappings.

The audit enumerates resources using read-only [LoadLibraryEx](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw) data/image-resource mappings. Installed ExplorerFrame.dll contains ordinary icon groups, address/navigation/search bitmap strips, and 324 PNG command images under the separate named resource type `IMAGE`. An initial icon-group-only inventory missed those command images; the full resource-type inventory corrects that limitation. DLL and associated SystemResources MUN mappings expose the same installed icon groups. Extraction creates memory DCs/DIBs only, with no visible UI, clipboard or global Shell operation. Alpha encoding is checked for each resource family: PNG WIC decoding and icon drawing are distinct from the raw bitmap strips described below.

Native `IMAGE` resources resolve the Easy access difference. ExplorerFrame.dll `IMAGE` 60045 is the stock folded-page/blue-marks artwork at 16 pixels; 60046/60047 are 20/24 pixels, 60048/60049 are 32, 60050 is 40, 60051 is 48, and 60052 is 64. The native 16-pixel PNG compared with the 2024 Home source crop (534,110)-(550,126) scores RGB RMSE 3.19. Generic Windows.organize shell32,-16753 scores approximately 42 and shows layered pages instead. The runtime can read `IMAGE` with FindResource/LoadResource and decode its PNG through public WIC; no extracted Windows asset belongs in the repository.

The Computer Open Settings artwork is a white gear on a blue square. Installed shell32,-16826 and C:\Windows\ImmersiveControlPanel\SystemSettings.exe,-10 are pixel-identical at 16 and 32 pixels. shell32,-16781 is a folder/green-arrow and is incorrect. The PCassist Computer source uses the same artwork family but a brighter blue background/edge rendering; the installed 19045 image has RGB RMSE 50.29 at the measured 32-pixel source crop, so cross-revision pixel identity is not established.

The same native resource-type inventory finds modern outline search-lens artwork in explorer.exe `IMAGE` 163-174: 16,20,24,25,30,32,40,48,50,60,64,80 pixels. These are runtime-native candidates for the address/search chrome; placement and source pixel equivalence require the chrome capture check. ExplorerFrame command PNG aliases also closely match existing DLL icons: Email 60056/60057 and 60064/60065 are pixel-identical to shell32,-265 at32; Properties60112/60132, Paste60012, Delete60024, SpecificPeople60072/60073 and Sort60080/60081 retain the same artwork family. Raw measurements and all resource sizes remain in ignored artifacts/icon-audit.

ExplorerFrame `RT_BITMAP` 288 contains straight BGRA pixels, rather than the premultiplied alpha required by [AlphaBlend](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-alphablend). Its 16-pixel Refresh cell is `(32,0)-(48,16)` and its History arrow is `(48,0)-(64,16)`. Partially transparent Refresh pixels retain RGB 128 even when alpha is 1, 19 or 43; 27 pixels have a color channel greater than alpha. The loader must premultiply once when creating the cached drawing bitmap, then preserve the native color and alpha. Treating these raw bytes as premultiplied produced a 14.53 RGB RMSE against the stock 2024 Refresh crop; the correctly interpreted native image scores 1.57. The native Up icon, shell32,-16817 at 16 pixels, scores 1.59 against the corresponding crop. ExplorerFrame bitmap 580 uses the same straight-alpha encoding for its six 16-pixel navigation cells. These are installed-build observations, and loaders validate the resource layout before drawing; a source JPEG and a different Windows revision do not establish whole-window pixel equality.

The installed `UIFILE` resource `EXPLORER_RIBBON` also loads successfully through the public [IUIFramework::LoadUI](https://learn.microsoft.com/en-us/windows/win32/api/uiribbon/nf-uiribbon-iuiframework-loadui). A logging-only private-desktop probe on build 19045 returned S_OK, reported a native Ribbon height of 147 pixels at 96 DPI, and captured the real native caption, tabs and group templates. Its 306 readable command symbols map to every one of the 131 numeric IDs initially created through IUIApplication::OnCreateUICommand, with zero unmatched IDs. For example, Home is 0x1001, Copy is 0x3023, Paste is 0x3020 and Undo is 0x3F00. These IDs are observations of the installed resource, not a Microsoft guarantee of a stable Explorer command ABI. A runtime adapter needs compatibility validation and a fallback; the binary resource and Windows artwork are not redistributed.

Application modes are process-local [IUIFramework::SetModes](https://learn.microsoft.com/en-us/windows/win32/api/uiribbon/nf-uiribbon-iuiframework-setmodes) bit masks. All 32 single bits and 112 ordinary-tab/modifier combinations were checked with windowless MTA UI Automation while the private STA pumped messages. Public UI_PKEY_ContextAvailable=NOTAVAILABLE hides contextual tabsets. The observed ordinary bases are 0x1 for Home/Share/View, 0x2 for Network/View, 0x4 for Computer/View and 0x8 for HomeGroup/View. On Home, 0x20 adds Open with History, 0x40 selects Open without History, 0x80 adds New and 0x100 selects New without Sync. Combined 0xA1 produces Clipboard, Organise, New, Open and Select in native order. Share Send uses modifier 0x20000 or 0x40000; Computer Network uses 0x2000 or 0x4000; Network's Network group uses 0x200 or 0x400. Modifier alternatives require capability selection rather than enabling both templates. Bit 25 (0x02000000) adds the native Backup group after Select on Home. The installed Backup Tools contexts are 0x800 and 0x810, with tabs 0x1802 and 0x1810; actual provider availability and account state must determine whether those contexts appear. Each probe returned S_OK and its visibility guard found no input-desktop windows. Dummy command properties leave action text/images empty, so these tests establish the actual stock templates and mode behavior, rather than a fully functional Explorer host.

Native File menu command `cmdFrequentPlaces` (0x5080) requests public UI_PKEY_RecentItems with VT_ARRAY|VT_UNKNOWN even though OnCreateUICommand reports it as an anchor. The native Quick Access Toolbar (0x5FFF) requests UI_PKEY_ItemsSource with an IUICollection. A separate logging-only native host verified the actual Frequent folders pin callback on a private desktop, with two mock items and no Shell identities or operations. The row's public LegacyIAccessible interface exposes a child push button (ROLE_SYSTEM_PUSHBUTTON), whose public accDoDefaultAction changes its STATE_SYSTEM_PRESSED state. On menu teardown, the framework calls Execute for 0x5080 with UI_PKEY_RecentItems and a VT_ARRAY|VT_UNKNOWN value. Its SAFEARRAY has ten slots even when the source supplied only two; both source slots returned the correct pin state, and the eight padding slots returned false. The probe asserted one pin callback, zero unrelated actions, both expected pin states and unchanged input-desktop isolation. A production decoder must retain the displayed source count and avoid passing padding indices to its actual folder-pin callback. This establishes the native event contract; normal Shell pin invocation remains separately guarded in headless tests. The public [Recent Items contract](https://learn.microsoft.com/en-us/windows/win32/windowsribbon/windowsribbon-controls-recentitems) and [UI_PKEY_RecentItems](https://learn.microsoft.com/en-us/windows/win32/windowsribbon/windowsribbon-reference-properties-uipkey-recentitems) describe the framework's property set and array model.

The production NativeRibbon decoder now retains the supplied pin states, examines only those source rows, and calls the host only for an actual change. tests/ribbon_recent_items_tests.cpp verifies this through real native menu and MSAA pin actions against the production class. On build 19045, all four authored-layout cases and all four installed-layout cases passed: unchanged two-item list, pin, unpin, and two presses that restore the original state. Each case asserts the final native pressed state, exact changed source index/count, preservation of the other pin, initializing-STA callback, zero unrelated actions and unchanged input-desktop isolation. No folder or Shell pin is invoked: the only target is the owned mock model. The source-count and no-change cases specifically detect the native padding regression.

Technical behavior remains tied to Microsoft's public contracts. A [Shell link](https://learn.microsoft.com/en-us/windows/win32/shell/links) may target any Shell namespace object, so a filesystem-only shortcut implementation is insufficient. Native target identity and selected-item providers should determine Open location and the additional applicable contextual pages. [Network Explorer](https://learn.microsoft.com/en-us/windows/win32/wsdapi/troubleshooting-the-network-explorer) uses the installed discovery providers; the [PnP-X presentation URL property](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/fundisc/pnp-x-provider-pkeys) represents the device's controlling web page. Provider-owned targets and state remain authoritative for these commands. Microsoft's [Windows 10 Backup instructions](https://support.microsoft.com/en-us/windows/experience/backup-recovery/back-up-and-restore-with-windows-backup) describe personal-account and OneDrive dependencies; those instructions do not prove that every user has an enabled Explorer Backup Tools context. This audit made no settings changes, discovery requests, Shell command invocations or account modifications.

The process-local Ribbon feature detector uses documented installed metadata once at Ribbon construction. [GetProductInfo](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getproductinfo) supplies the native client SKU, and Microsoft's [BitLocker edition support table](https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/) distinguishes ordinary Pro, Education and Enterprise tools from Home device encryption. An unclassified or Server SKU retains a conservative capability with ERROR_NOT_SUPPORTED provenance: edition metadata alone does not establish whether an optional Server component is installed. Native provider state still determines each drive action.

Media availability is established by System32-only runtime loading of mfplat.dll and public [MFStartup](https://learn.microsoft.com/en-us/windows/win32/api/mfapi/nf-mfapi-mfstartup) with MF_VERSION and MFSTARTUP_LITE, which omits socket initialization. Each successful startup is balanced immediately by [MFShutdown](https://learn.microsoft.com/en-us/windows/win32/api/mfapi/nf-mfapi-mfshutdown); no playback, media session or device enumeration occurs. [SHRestricted](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shrestricted) supplies the administrator's REST_NOCDBURNING policy, and actual System32 cleanmgr.exe file metadata supplies cleanup availability. The burning flag describes policy permission rather than optical hardware support. Known component absence returns false with its native HRESULT; other failed checks retain conservative true and the diagnostic error. No policy or user registry value is written.

tests/ribbon_features_tests.cpp passed headlessly on Home build 19045, detecting product 101, no ordinary BitLocker tools, and available Media Foundation, unrestricted burning policy and cleanmgr.exe. Its separate caller-owned Media Foundation startup remains usable across three detector calls through owned empty work-queue allocation; after caller shutdown, MF_E_SHUTDOWN proves the detector retained no startup references. Null output, filled per-check HRESULTs, actual SKU/policy/executable agreement, unchanged settings and clipboard sequence, and no process window on the input desktop are also asserted. No drive, device, cleanup utility or Shell action is invoked by this test.
