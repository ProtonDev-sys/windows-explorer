# Native file-operation verification

The new `native_shell_transfer` fixture is restricted to genuine disposable GitHub Actions execution plus explicit `WINDOWSEXPLORER_NATIVE_TRANSFER_TEST=1`. Its separate fresh-runner job requires an empty clipboard and native history before exercising real Copy/Cut/Paste, Paste Shortcut and breadcrumb destination `IDropTarget` Copy/Move/Link protocols. It verifies the original native data object's CIDA/effects, complete output bytes, native view membership and appropriate volume/FileID relationships. Direct drop protocols do not establish physical mouse drag behavior. Local execution skips before COM, windows or fixtures; the dedicated hosted positive run is still required.

Clipboard cleanup retains the exact object originally published by `OleSetClipboard`, verifies current ownership and guards reentrant publication with a generation counter. It never empties a later foreign producer or flushes the fixture's payload. Native operation and clipboard leases retain providers, views and owned source files until asynchronous completion and cleanup have been verified. The fixture initializes its private desktop before COM and observes both that desktop and the unchanged input desktop throughout creation and teardown.

The normal app routes Paste, Copy/Move menus, Delete/Permanent Delete and Undo/Redo through the installed Windows providers with the current selection and Shell view site. Native Delete supplies its own confirmation policy. Production undo uses Windows.undo/redo and native Shell records, verified separately by the dual-gated disposable-CI native-history fixture.

Direct ShellOperations copy/move/new-folder operations use public IFileOperation with an owner window, native progress/error/collision UI and FOFX_ADDUNDORECORD for normal reversible user operations. Silent fixture operations instead use FOF_NO_UI, FOFX_EARLYFAILURE and FOFX_NOCOPYHOOKS, omit native undo records and preserve copy/move collisions with extension-preserving generated names. These are [documented operation flags](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags). Silent tests never exercise recycling or the shared clipboard.

An optional public IFileOperationProgressSink is advised for the duration of a direct operation and unadvised before return. The native dialog remains available in ordinary operation. The internal sink retains individual operation failures, and GetAnyOperationsAborted is checked even when PerformOperations returns success. Microsoft documents that [success alone does not establish completion](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-getanyoperationsaborted).

The cancellation classifier recognizes ERROR_CANCELLED, E_ABORT and the SDK's COPYENGINE_E_USER_CANCELLED. It deliberately preserves COPYENGINE_E_CANCELLED as an engine failure. App error handling uses this distinction to avoid an additional error prompt after the user cancels native UI. This does not turn access failures or ignored-item success codes into user cancellation.

tests/shell_operations_tests.cpp adds a separate owned private-desktop STA for real native callback verification. It cancels before copy, move, rename, new-folder creation and owned permanent deletion, then verifies original identities/content and absent outputs. A post-copy cancellation preserves exactly one completed copy and both sources while stopping the remaining batch. A separate E_ACCESSDENIED callback remains an actual failure. These are callback cancellations, using the documented [pre-item](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperationprogresssink-precopyitem) and [post-item](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperationprogresssink-postcopyitem) contracts; no user cancellation dialog is automated.

Successful fixtures verify actual Unicode collision names/extensions, untouched collision identities, native post-operation targets and content, same-volume move/rename identity, new-folder identity and permanent-delete completion. The recorded Windows 10 Home build 19045 callback run delivered sixteen progress updates from five native operations on the initializing STA. It created no visible input-desktop window and left the clipboard sequence unchanged. Current full-suite results are reported in [verification](verification.md).

ShellOperations::invoke now uses the existing retained NativeContextMenu, with an optional actual IShellView site. Public [IObjectWithSite::SetSite](https://learn.microsoft.com/en-us/windows/win32/api/ocidl/nf-ocidl-iobjectwithsite-setsite) attaches the supplied site before querying and detaches it after destroying the menu. The helper finds a unique enabled canonical leaf through [GetCommandString](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-icontextmenu-getcommandstring), then invokes its actual numeric [menu identifier offset](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-icontextmenu-invokecommand). The provider's default association and returned HRESULT remain authoritative.

Seven entirely mocked selection/provider cases exercise that same helper on the private desktop: localized default Open, disabled, duplicate, stale-disabled and missing canonical entries, query failure and native user cancellation. They verify the exact ordinal, owner, site lifetime, fresh menu-state validation and failure propagation. No native association, application or Shell command is launched by those tests. Actual GUI collision/confirmation workflows and global history are separate native-provider behavior; this checkpoint does not claim to automate those dialogs or change their shared state.
