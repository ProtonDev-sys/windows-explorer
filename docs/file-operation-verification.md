# Native file-operation verification

The normal app routes Paste, Copy/Move menus, Delete/Permanent Delete and Undo/Redo through the installed Windows providers with the current selection and Shell view site. Native Delete supplies its own confirmation policy; the older Host confirmation branch is bypassed by that catalogue dispatch. Production undo uses Windows.undo/redo and native Shell records. It does not substitute the isolated test journal for the user's native history.

Direct ShellOperations copy/move/new-folder operations use public IFileOperation with an owner window, native progress/error/collision UI and FOFX_ADDUNDORECORD for normal reversible user operations. Silent fixture operations instead use FOF_NO_UI, FOFX_EARLYFAILURE and FOFX_NOCOPYHOOKS, omit native undo records and preserve copy/move collisions with extension-preserving generated names. These are [documented operation flags](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags). Silent tests never exercise recycling or the shared clipboard.

An optional public IFileOperationProgressSink is advised for the duration of a direct operation and unadvised before return. The native dialog remains available in ordinary operation. The internal sink retains individual operation failures, and GetAnyOperationsAborted is checked even when PerformOperations returns success. Microsoft documents that [success alone does not establish completion](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-getanyoperationsaborted). A cancelled or partial silent fixture never produces a complete journal transaction.

The cancellation classifier recognizes ERROR_CANCELLED, E_ABORT and the SDK's COPYENGINE_E_USER_CANCELLED. It deliberately preserves COPYENGINE_E_CANCELLED as an engine failure. App error handling uses this distinction to avoid an additional error prompt after the user cancels native UI. This does not turn access failures or ignored-item success codes into user cancellation.

tests/shell_operations_tests.cpp adds a separate owned private-desktop STA for real native callback verification. It cancels before copy, move, rename, new-folder creation and owned permanent deletion, then verifies original identities/content and absent outputs. A post-copy cancellation preserves exactly one completed copy and both sources while stopping the remaining batch; no fixture history is recorded. A separate E_ACCESSDENIED callback remains an actual failure. These are callback cancellations, using the documented [pre-item](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperationprogresssink-precopyitem) and [post-item](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperationprogresssink-postcopyitem) contracts; no user cancellation dialog is automated.

Successful fixtures verify actual Unicode collision names/extensions, untouched collision identities, native post-operation targets and content, same-volume move/rename identity, new-folder identity and permanent-delete completion. On Windows 10 Home build 19045, five native operations delivered sixteen progress updates on the initializing STA. The process created no visible input-desktop window and left the clipboard sequence unchanged. Together with the original operations and conservative journal fixtures, all thirteen groups passed in 0.47 seconds without compiler warnings.

ShellOperations::invoke now uses the existing retained NativeContextMenu, with an optional actual IShellView site. Public [IObjectWithSite::SetSite](https://learn.microsoft.com/en-us/windows/win32/api/ocidl/nf-ocidl-iobjectwithsite-setsite) attaches the supplied site before querying and detaches it after destroying the menu. The helper finds a unique enabled canonical leaf through [GetCommandString](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-icontextmenu-getcommandstring), then invokes its actual numeric [menu identifier offset](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-icontextmenu-invokecommand). The provider's default association and returned HRESULT remain authoritative.

Seven entirely mocked selection/provider cases exercise that same helper on the private desktop: localized default Open, disabled, duplicate, stale-disabled and missing canonical entries, query failure and native user cancellation. They verify the exact ordinal, owner, site lifetime, fresh menu-state validation and failure propagation. No native association, application or Shell command is launched by those tests. Actual GUI collision/confirmation workflows and global history are separate native-provider behavior; this checkpoint does not claim to automate those dialogs or change their shared state.
